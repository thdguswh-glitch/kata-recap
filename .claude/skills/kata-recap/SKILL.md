# 카타 정리

아티클 카타에서 팀이 원문을 읽고 개인 정리와 토의를 마친 뒤, 이 스킬로 논의를 정리한다. 정리 결과를 보고 튜터가 피드백을 준다. 그래서 마지막에 튜터에게 드릴 질문을 정리하는 것이 핵심이다. 출력은 한국어로 쓴다.

## 입력

- **원문:** 링크 또는 본문으로 함께 받는다. 링크면 읽는다. 읽을 수 없으면 제목만 보고 짐작해서 요약하지 않고, 원문 본문을 붙여 달라고 요청한다.
- **팀원 개인 정리:** 팀원이 원문을 읽고 적은 정리다. 핵심 내용, 흥미로운 점, 궁금한 점이 들어 있다.
- **토의 내용:** 채팅 스레드나 메모 형태다.
- **튜터 답변:** 입력에 섞여 있어도 정리에 반영하지 않는다. 이 스킬은 튜터 답변을 받기 전의 논의를 정리한다.

입력을 읽을 때 다음을 지킨다.

- 취소선(`~~…~~`) 내용은 팀이 뺀 것이므로 제외한다. Notion 마크업과 이미지는 무시한다.
- 팀원 이름은 토의에 쓰인 표기로 통일한다. 이름 없는 발언은 "한 팀원"으로 쓰고 추측하지 않는다.
- 농담이나 가벼운 말투로 쓴 글이라도 의견이 담겨 있으면 반영한다. 의견이 없는 잡담만 제외한다.
- 동의 반응을 텍스트로 남기지 않는 경우가 많다. 기록에 동의 표시가 없다고 반대나 무관심으로 보지 않는다.

## 원칙

1. **출처별 기준을 지킨다.** 요약과 핵심 논지는 원문 기준으로, 인사이트와 피드백 질문은 팀원 정리 기준으로 쓴다.
2. **논의되지 않은 내용을 논의된 것처럼 쓰지 않는다.** 원문에만 있고 팀원 중 아무도 짚지 않은 내용은 논의 섹션에 넣지 않는다.
   - 2-1. 논의하지 않은 주제와 내용을 생성하지 않는다.
   - 2-2. 팀 논의 중 결론이 나오지 않은 내용을 찾아준다. 의견이 갈렸거나, 질문만 남았거나, "더 이야기해 보자"로 끝난 부분을 찾아 "피드백 질문 정리"로 연결한다. 결론을 대신 내리지 않고, 팀원 정리에 근거가 있는 것만 적는다.
   - 2-3. "합의", "결론", "다수" 같은 표현은 기록에 근거가 있을 때만 쓴다. "여러 명"이라고 쓰기 전에 실제로 몇 명이 말했는지 센다. 구두로 이뤄졌을 수 있는 동의는 추정하지 않는다. 합의 여부가 불분명하면 "확인 필요"로 표시하거나 사용자에게 묻는다. "가장 비판적인 논점" 같은 평가 라벨은 붙이지 않는다.
3. **팀원 정리가 원문과 다르면 원문을 따르고, 다르다고 알려준다.** 어떤 부분이 어떻게 다른지 사용자에게 밝힌다. 팀원 정리를 조용히 고치지 않는다. 팀원 정리끼리 서로 다른 부분(수치, 사실)도 원문으로 확인해서 알려준다.
4. **비슷한 의견은 하나로 묶고, 질문과 개인 경험은 따로 살린다.** 여러 명이 비슷하게 말한 건 한 항목으로 합치고 괄호에 이름을 적는다. 질문과 개인 경험은 합치지 않고 말한 사람 이름과 함께 남긴다.
5. **원문만 받았다면 핵심 논지만 먼저 쓴다.** 팀 논의는 지어내지 않는다.

## 입력별 동작

- **원문만 있을 때:** 제목, 핵심 논지(요약 포함)만 쓴다. 인사이트와 피드백 질문은 "팀원 정리가 아직 없음"이라고 쓰고 비워 둔다. 정리를 받으면 이어서 완성하겠다고 안내한다.
- **원문과 팀원 정리·토의가 모두 있을 때:** 아래 출력 구조 전체를 쓴다.
- **팀원 정리·토의만 있을 때:** 원문을 요청한다. 먼저 쓸 수 있는 인사이트와 피드백 질문만 쓰고, 핵심 논지는 "원문이 없어 생략"이라고 표시한다.

## 출력 구조

```
# [아티클 제목] 카타 정리
원문: [링크]

## 핵심 논지
(원문 기준. 첫 문단은 요약 3~5문장, 이어서 핵심 논지)

## 인사이트
(팀 논의 기준. 번호 + 굵은 소제목 + 불릿)

## 피드백 질문 정리
(튜터에게 드릴 질문. 팀 논의에서 질문으로 남았거나 결론이 나지 않은 것)

## 원문과 다르게 정리된 부분
(있을 때만)

## 원문에는 있지만 논의되지 않은 내용
(있을 때만. 한두 줄로 짧게)
```

## 출력 형식 (고정)

- 섹션 제목 문구와 순서는 위 구조를 그대로 쓴다.
- 불릿은 `-`만 쓴다. 수치나 비교는 표로 써도 된다.
- 이름은 정리에 적힌 그대로 괄호에 쉼표로 구분한다. 예: (민수, 지은)
- 문체는 평서문으로 통일한다. 예: "~라는 의견이 있었다", "~가 제안됐다"
- 내용이 없는 섹션은 빈 칸으로 두지 말고 통째로 생략한다. 단, 입력이 부족해서 비운 경우에는 "입력별 동작"의 안내 문구를 쓴다.
- 원문의 표현을 길게 옮기지 말고 요약한다.

## 섹션별로 넣는 것 / 넣지 않는 것

- **핵심 논지:** 원문의 주장, 근거, 수치를 쓴다. 팀 논의는 넣지 않는다. 항목당 한 문장으로 쓴다.
- **인사이트:** 논의에서 나온 시사점과 적용 아이디어를 쓴다. 번호마다 팀이 말한 주장을 굵은 소제목으로 쓰고, 아래에 논의 내용(이름)을 불릿으로 쓴다. 개인 경험과 질문은 "경험:", "질문:"으로 따로 표시한다. 원문 내용은 넣지 않는다. 개수는 논의된 만큼 쓰고 억지로 채우지 않는다.
- **피드백 질문 정리:**
  - 팀원이 낸 질문과 논의 끝에 남은 의문만 쓴다. 새 질문을 만들지 않는다.
  - 질문은 튜터가 답할 수 있게 한 문장으로 다듬되, 팀원의 의도를 바꾸지 않는다. 비슷한 질문은 하나로 묶고 질문자 이름을 적는다.
  - 질문마다 배경(어떤 논의에서 나왔는지, 팀원들이 짐작한 내용)을 한두 줄로 붙인다. 짐작은 짐작이라고 쓴다.
  - 원문으로 답이 확인되는 질문은 목록에서 빼고, 원문 어디에 답이 있는지 한 줄로 알린다. 원문에 답이 없다고 확인한 경우에만 "원문에 서술 없음"이라고 쓴다.
- **원문과 다르게 정리된 부분:** 원문 기준으로 바로잡은 내용과 이유를 쓴다.
- **원문에는 있지만 논의되지 않은 내용:** 한두 줄로 짧게 쓰고, 제목에서 논의되지 않았음을 분명히 한다.

무엇을 핵심으로 볼지, 어떻게 묶을지, 항목을 몇 개로 할지는 자료에 맞게 판단한다.

## 경계 사례

- 한 사람만 말한 의견은 묶지 않고 이름과 함께 단독 항목으로 쓴다.
- 팀원이 추측으로 말한 내용은 추측이라고 표시한다. 사실처럼 쓰지 않는다.
- 팀원끼리 같은 말을 다른 표현으로 했다면 하나로 묶되, 표현이 달랐던 점은 버리지 않는다.
- 팀원 정리에 없는 의견, 수치, 결론을 덧붙이지 않는다. 확실하지 않으면 사용자에게 묻는다.

## 출력 전 점검

내보내기 전에 아래를 확인한다.

- 섹션 순서와 제목이 출력 구조와 같은가
- 원칙 2를 어긴 문장은 없는가 (논의되지 않은 내용, 근거 없는 합의·다수 표현, 대신 내린 결론)
- 팀원 정리와 원문이 다른 부분, 팀원 정리끼리 다른 부분을 짚었는가
- 개인 정리와 토의에서 나온 질문을 빠뜨리지 않았는가
- 튜터 답변을 반영하지 않았는가
